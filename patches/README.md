# patches/

Патчи, которые применяются во время сборки. Их три вида, и они применяются
на разных этапах.

| Где лежит | К чему применяется | Когда | Если не применился |
|---|---|---|---|
| `patches/*.patch` | к дереву исходников OpenWrt / ImmortalWrt (`openwrt/`) | шаг **Apply custom patches** в `Universal_WRT_Builder.yml`, до `feeds update` | сборка останавливается |
| `patches/feeds/<фид>/*.patch` | к фиду `feeds/<фид>/` | `sh/WRT-part2.sh`, между `feeds update` и `feeds install` | файлы патча изменились у автора — сборка останавливается до компиляции, уведомление в Telegram (см. «Сверка с исходниками»); иначе предупреждение и сборка без патча (стоп при `FEED_PATCH_STRICT=1`) |
| `patches/packages/<пакет>/*.patch` | к пакету, который `sh/WRT-part3.sh` клонирует в `package/<пакет>` (или к нему же в фиде) | `sh/WRT-part3.sh`, сразу после клонирования | так же, как у патчей фидов (сверка — только для пакетов в `package/`) |

**Включение и отключение.** Все три вида отключаются разом полем формы
`apply_patches` (в режиме `combo` — полем `patches` каждой сборки матрицы в
`Universal_WRT_Builder.yml`). При отключении шаг **Apply custom patches**
ничего не применяет, каталог `patches/` на время `WRT-part2.sh`/`WRT-part3.sh`
скрывается (и возвращается в конце шага, даже при ошибке). Вариант `forkop`
(и `forkop-mod`) при этом собирается из голого репозитория фида (см. ниже) —
job `setup` предупреждает, чем это грозит. В имени артефакта сборки стоит
`patches` или `nopatches`.

## Сверка с исходниками: патч устарел — сборка стоп

Фиды (`forkop`, `podkop`, `netshift`…) и пакеты в `package/` берутся с
ветки автора, поэтому код под патчами меняется без нас. Патч при этом может
ещё ложиться со сдвигом строк, а правка — встать не туда или потерять смысл.
Поэтому перед применением каждого патча `sh/patch-drift.sh` сравнивает
файлы, которые он правит, с теми, на которые он написан:

- эталон — строка `index <хеш до>..<хеш после>` в каждом diff патча (git
  кладёт её сам), отдельного списка нет: обновили патч — обновился эталон;
- текущий файл хешируется `git hash-object`; хеш другой — у автора файл
  изменился, патч **не применяется** и попадает в `patch_drift.txt`;
- следующие патчи той же серии, которые правят тот же файл или требуют
  (`Requires:`) пропущенный, тоже попадают туда с пометкой «после
  пропущенного патча» / «требует устаревший патч» — перевыпускать их надо
  вместе;
- патч, который уже есть в исходниках (автор внёс то же самое), — как и
  раньше, пропуск без остановки.

После `WRT-part3.sh` шаг **Update Feeds & Config** видит непустой
`patch_drift.txt` и останавливает **эту** сборку до компиляции (остальные
сборки матрицы идут дальше), а шаг **Telegram — патчи надо обновить** шлёт
список: фид или пакет, патч и изменившиеся файлы. Дальше патчи нужно
перевыпустить под новый код автора и проверить.

Не сверяются патчи пакета, найденного внутри чужого фида
(`luci-app-homeproxy` в ImmortalWrt LuCI): это отдельная копия со своей
историей, для неё прежнее поведение с предупреждением. Выключить сверку —
снять галочку `stop_outdated_patches` («Останавливать сборку, если патч
устарел») при запуске; по умолчанию она включена и действует на все сборки
запуска, в том числе в `combo`.

**Как перевыпускать патчи серии.** Каждый патч снимается с состояния
**после** предыдущих (`git diff` по очереди), иначе его «хеш до» не совпадёт
и сверка сработает ложно. Заголовок (`Subject`, описание, `Requires:`)
переносится как был.

## Патчи дерева: `patches/*.patch`

Берутся только файлы в корне каталога, подпапки не просматриваются (у
`patches/feeds/` и `patches/packages/` свои этапы). Применяются по алфавиту
командой

```sh
patch -p1 -d openwrt < patches/<файл>.patch
```

то есть пути в патче считаются от корня дерева OpenWrt
(`a/package/...`, `a/include/...`). Пример имени:
`001-mbedtls-fix-build-when-disabled.patch`.

На этом шаге фидов ещё нет, поэтому **патч к пакету из фида сюда класть нельзя**:
он не найдёт файлы и остановит все варианты сборки.

## Патчи фидов: `patches/feeds/<фид>/*.patch`

Имя подпапки должно совпадать с именем фида в `feeds.conf`
(первое слово после `src-git`). Пути в патче считаются от корня репозитория
фида (`a/forkop/Makefile`, `a/luci-app-forkop/...`).

`WRT-part2.sh` проходит патчи подпапки по порядку имён:

1. фида `feeds/<фид>` нет (вариант его не подключает) — пропускает всю подпапку;
2. патч уже есть в исходниках (автор внёс то же самое) — пропуск, `✓ ... уже есть`;
3. в заголовке патча есть строка `Requires: <имя патча>`, а тот патч не применён
   и не найден в исходниках — пропуск с предупреждением. Так зависимый патч
   не попадёт в код без того, на что он опирается;
4. патч применяется без сдвига контекста — применяется
   (`patch -p1 -F 0`: без «нечёткого» поиска места, чтобы при изменённом
   коде правка не встала не туда);
5. иначе — пропуск с предупреждением `::warning::` в Actions.

Каждый патч применяется целиком или не применяется вовсе. В конце выводится
итог: `>>> forkop: применено N, уже было M, пропущено K`. Чтобы сборка
останавливалась, если хоть один патч не применился, задайте переменную
окружения `FEED_PATCH_STRICT=1`.

### forkop (`patches/feeds/forkop/`, фид `forkop` → ushan0v/forkop)

Фид forkop выбирается полем формы **Build Variant**: `forkop` — оригинал,
`forkop-mod` — форк. Адреса фидов заданы в блоке `env:` в начале
`Universal_WRT_Builder.yml`:

```yaml
FORKOP_FEED_ORIG: "forkop https://github.com/ushan0v/forkop.git;main"        # вариант forkop
FORKOP_FEED_MOD: "forkopmod https://github.com/Gavr1024/forkop-mod.git;main" # вариант forkop-mod
```

Внутри сборки оба — вариант `forkop` (part2, part3 и `zz1` их не различают);
`forkop-mod` виден только в имени job и артефакта.

Больше ничего менять не нужно: `WRT-part2.sh` применяет подпапку
`patches/feeds/<имя фида>` только для загруженного фида (вторая пропускается с
сообщением «Фид '…' не загружен»), версию пакета берёт из тегов того же
репозитория, а предупреждения в Actions называют выбранный фид.

По умолчанию — оригинал `ushan0v/forkop`: в эти патчи перенесено всё рабочее
из форка (023, 024 и исправления 018, 019). Голый оригинал 1.0.5 без патчей
на sing-box 1.14 не запускается (issue #98), пока автор не внёс исправления, —
при `apply_patches=false` job `setup` об этом предупреждает.

### netshift (`patches/feeds/netshift/`, фид `netshift` → yandexru45/netshift)

Применяется, только если в форме выбран вариант `netshift`. netshift — форк
podkop с переименованием `podkop` → `netshift`, поэтому патчи podkop на него
не ложатся: часть их исправлений автор уже внёс сам (разбор ссылок с
`%40`/`%23`, IPv6, домены с заглавными буквами, «Торренты мимо прокси»,
порядок правил nft, таймауты загрузки, в 0.9.10 — транспорт `httpupgrade`,
пропуск ссылок с неизвестным транспортом и ссылки без `type`). Остальное
перенесено и проверено на 0.9.10 (`20553cc`); 08.10.2026 патчи перевыпущены
под `main` `e382e39` (после 0.9.10: блок «Окружение» в диагностике, удалено
правило resolve для IPv6-входа, проверка скачанных пакетов самообновления) —
содержимое прежнее, изменились только строки `index`.

| Патч | Что делает |
|---|---|
| 001 | разбор ссылок: socks5 — логин и пароль делились после декодирования, и закодированный `:` уезжал в чужое поле (`us%3Aer:p%3Aass` → логин `us`, пароль `er:p:ass`); VLESS/Trojan с транспортом `http` (h2) — sing-box его умеет, а 0.9.10 пропускает такую ссылку как неизвестную; ссылки без `security` больше не пишут ошибку в журнал. Синтаксис jq 1.7 (OpenWrt 24.10; автор заявляет поддержку 24.10+): `+` в значении поля `reality` (новая опция `reality_mlkem` в 0.9.10) — на jq 1.7 не строился ни один узел с TLS/Reality/Hysteria2; `reduce … (…) as $resolved` в разборе подписок — на jq 1.7 не работала ни одна подписка (и в 0.9.9). Только скобки, на jq 1.8.1 (OpenWrt 25.12) результат тот же байт в байт. Не перенесено: последовательный запуск start/reload (podkop 003). Гонка
возникает только с включённым «Мониторингом интерфейсов» (перезапуск по

заработает.

### Перезапуск и conntrack: какие варианты затронуты

При перезапуске прокси правила перехвата на несколько секунд снимаются, и
TCP-соединения, открытые в это окно, уходят напрямую через masquerade.
Дальше всё зависит от того, как вариант перехватывает TCP:

- **redirect (DNAT в nat-цепочке)** — homeproxy, Re:HomeProxy (режимы
  `redirect_*`), passwall2 (по умолчанию). NAT выбирается по первому пакету,
  поэтому «утёкшее» соединение остаётся прямым до закрытия. Исправляется
  патчами HomeProxy 007, Re:HomeProxy 004 и passwall2 001;
- **TPROXY, метка на каждый пакет** — podkop, netshift, forkop, forkop-mod,
  trafira, luci-app-xray. Как только правила возвращаются, следующий пакет
  «утёкшего» соединения уходит в ядро, ядро отвечает RST, и клиент
  переподключается через прокси. Патч не нужен;
- **метка только на SYN** — v2rayA (и режим redirect, и TPROXY) и passwall2
  в режиме TPROXY. «Утёкшее» соединение остаётся прямым до закрытия.
  v2rayA ставит правила сам (Go-сервис), патч к пакету не делался: после
  переключения прокси в его веб-интерфейсе, если сайты не открываются,
  выполните `conntrack -D -p tcp --src-nat`.

Проверено на стенде из трёх сетевых пространств имён (клиент, роутер,
сервер) с conntrack-tools 1.4.8, как на роутере: соединение, открытое до
появления redirect, после него продолжало идти на сервер напрямую; после
`conntrack -D -p tcp --src-nat` оно сбрасывалось, переподключение уходило в
redirect, а прямое соединение, соединение через redirect и собственное
соединение роутера продолжали работать. С правилами в стиле podkop (метка
и TPROXY на каждый пакет) «утёкшее» соединение сбрасывалось сразу после
возврата правил, без патча.

## Патчи пакетов: `patches/packages/<пакет>/*.patch`

Для пакетов, которых нет в фидах и которые `WRT-part3.sh` клонирует в
`package/` (сейчас это HomeProxy из `immortalwrt/homeproxy` и Re:HomeProxy из `1andrevich/homeproxy-hiddify`). На этапе патчей
фидов их ещё нет, поэтому применяются они в part3, сразу после клонирования.
Имя подпапки — имя каталога пакета. Каталог ищется в `package/<пакет>`, затем
в фидах: на ImmortalWrt HomeProxy лежит в `feeds/luci/applications/`, и
патчи ложатся туда же. Пути в патче считаются от корня репозитория пакета
(`a/htdocs/...`, `a/root/...`). Правила те же, что у патчей фидов: уже есть в
исходниках — пропуск, не подходит — `::warning::` и сборка дальше
(`FEED_PATCH_STRICT=1` — остановка), CRLF снимается. Строки `Requires:` не
поддерживаются: патчи пакета должны быть независимыми.

## Как сделать новый патч

К дереву OpenWrt:

```sh
git clone --branch openwrt-25.12 https://github.com/openwrt/openwrt.git && cd openwrt
# правки…
git diff > ../patches/002-описание.patch
```

К фиду (пример для forkop):

```sh
git clone https://github.com/ushan0v/forkop.git && cd forkop
# правки…
git diff > ../patches/feeds/forkop/025-описание.patch
```

Проверка на свежем клоне фида, без правок:

```sh
patch -p1 -F 0 --dry-run -d forkop-clean < patches/feeds/forkop/025-описание.patch
```

Файлы применяются по алфавиту, поэтому начинайте имя с номера (`001-`, `002-`…).
